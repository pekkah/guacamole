# Changelog

All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.0.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Breaking

- **Namespaces consolidated.** The `Core` segment is gone and user-facing types moved to `Guacamole`, so `using Guacamole;` is enough for typical code: sources and their extensions (`Guacamole.Sources`), `Result<TValue, TError>` (`Guacamole.Core.Common`), `ComputationError` (`Guacamole.Core.Pipeline`), `ProviderMetadata`/`SourceLocation` (`Guacamole.Core.Diagnostics`) and `ContextOperationException` (`Guacamole.Exceptions`, since removed) are now in `Guacamole`. Advanced types moved to `Guacamole.Pipeline` (from `Guacamole.Core.Pipeline` and `Guacamole.Core.Nodes`), `Guacamole.Caching` (from `Guacamole.Core.Caching`) and `Guacamole.Diagnostics` (`GuacamoleMetrics`, `MetricsConfiguration`). Generated code references the new namespaces. See [MIGRATION_GUIDE.md](MIGRATION_GUIDE.md#namespace-consolidation).
- **Internal plumbing is no longer public.** Made `internal`: the computation graph (`ComputationGraph`, including the test-only `ReplaceNode`/`WithCachedValue` and the mutable `ValueCache`), the node types (`IComputationNode`, `IComputationNode<T>`, `ICollectionComputationNode<T>`, `IHasComparer<T>`, `ComputationContext`, `ComputationNodeBase<T>`, `CollectionComputationNodeBase<T>`), `VersionTracker`, `NodeVersionInfo`, the cache (`ICache`, `LRUCache`, `ICacheStatisticsProvider`, `CacheStatistics`), the providers' `Node`/`Graph` properties and constructors, the concrete `IncrementalSource<T>`, `IncrementalValueSource<T>` and `BatchOperation<T>` (use the interfaces), `ComputingContextBase.Graph`/`SubscribeToSource`, the node-based DI factories (`IComputationContextFactory`, `IIncrementalValueProviderFactory`, `IIncrementalValuesProviderFactory`) and the `GuacamoleMetrics` recording helpers. Contexts now create their sources with the new protected `ComputingContextBase.CreateSource<T>`/`CreateValueSource<T>` helpers, which the generated constructor calls. See [MIGRATION_GUIDE.md](MIGRATION_GUIDE.md#internal-types-and-members).
- **Single-value `Where` produces "no value" instead of an error.** `Result<TValue, TError>` has a third state, None (`Result.None`, `IsNone`, `IsError`, three-way `Match`; `default` is None). A rejected value propagates as None through `Select`/`Where`/`Combine` without running their lambdas (errors take precedence in `Combine`), `SelectMany` and `values.Combine(value)` produce no items, and output handlers are not called (they fire again when a value reappears). `IncrementalValueProvider<T>.Value` throws `InvalidOperationException` for no value; the new `TryGetValue(out T)` returns `false` instead. See [MIGRATION_GUIDE.md](MIGRATION_GUIDE.md#single-value-where-produces-no-value).
- **Collection sources enumerate in insertion order.** `IIncrementalSource<T>` used a hash set, so `GetSnapshot()`, `.Values` and `Collect()` were in hash order, which varies between runs for strings (randomized hash codes). Items are now kept in insertion order with set semantics unchanged: `Push` appends, `Replace` keeps the replaced item's position, and `Remove` followed by `Push` appends. Results built from collections (for example `Collect()`) are therefore deterministic for a given sequence of operations (#25). See [MIGRATION_GUIDE.md](MIGRATION_GUIDE.md#collection-sources-keep-insertion-order).
- **Settings that had no effect were removed.** `CacheOptions` (`DefaultCapacity`, `EnableStatistics`, `CleanupIntervalMs`), `PipelineOptions` (`MaxDependencyDepth`, `EnablePerformanceMetrics`, `ComputationTimeoutMs`), `ProviderOptions.EnableProfiling`/`EnableMetadataTracking`, the unused DI registrations (`ICache`, `ICacheStatisticsProvider`, `ComputationGraph`, node-based factories), `MetricsConfiguration.EnableDetailedTracing`/`TracingSampleRate`/`MaxTrackingNamesPerProcess`/`EnableProviderMetrics`/`EnableMemoryMetrics`/`MinimumDurationThresholdMs`/`RecordIndividualNodePerformance`/`TrackInvalidationCascades`/`IsValid()`, and the never-recorded instruments `CacheInvalidationsTotal`, `ProviderTransformationsTotal`, `ProvidersCreatedTotal` and `MemoryUsageEstimated`. Dead code removed: `ComputingContextBase.Lock` and its private `InvalidateNodeCache`, `ContextOperationException`, `ComputationGraph.IsValidDAG`/`ValidateDependencies`/`IsNodeRegistered`, unused `VersionTracker` members. See [MIGRATION_GUIDE.md](MIGRATION_GUIDE.md#removed-settings-and-dead-code).

### Added

- **`ComputingContextBase.TrimUnusedNodes()`** (#41): removes pipeline nodes that are no longer referenced by any provider, output registration or downstream node from the context's graph, together with their cached values and version records, and returns how many it removed. The runtime node registry, the evaluation handles and cached values no longer keep nodes alive by themselves; the node-reuse cache keeps operator nodes alive until the next trim (and again whenever an identical call requests them). Pipelines built dynamically (capturing lambdas, per-request pipelines) therefore stay bounded when trimmed periodically. A node that is still referenced, and the nodes it reads, are never removed; a removed node requested again by an identical operator call is recreated with an empty cache.
- **Automatic trimming** (#52): override `ComputingContextBase.AutoTrimInterval` (default `0`, off) to have the context run `TrimUnusedNodes()` itself after every N pipeline nodes added to its graph, so long-running hosts that build pipelines dynamically stay bounded without explicit calls. Only newly added nodes are counted (one interlocked increment each; reads are unaffected); when many nodes remain registered, the next trim waits for at least half as many new nodes, keeping the cost proportional to the nodes added. Trims never start inside a node computation and never block (a concurrent trim makes the next new node try again). Nodes released by one automatic trim are removed by a later one once collected. Behaviour is unchanged when off.
- **Configurable cache capacity**: override `ComputingContextBase.CacheCapacity` (default `ComputingContextBase.DefaultCacheCapacity`, 10,000) to size a context's value cache; it was hardcoded before.
- **Computation metrics**: providers record `GuacamoleMetrics.ComputationsTotal`, `ComputationDuration` and `ComputationErrors` whenever they compute a value (cache hits excluded), controlled by `MetricsConfiguration.EnableComputationMetrics`, with optional `tracking.name`/`pipeline.stage` dimensions.
- **Cross-item lookup guidance** (#25): new "Cross-item lookups (e.g. symbol tables)" sections in the [Performance Guide](docs/performance-guide.md#cross-item-lookups-eg-symbol-tables) and Quickstart, and a runnable [`examples/CrossFileSymbolsExample`](examples/CrossFileSymbolsExample/): compute data shared across items with `Collect()` and a deterministic merge into a type with structural equality, `Combine` it with each item, and optionally narrow it per item, instead of accumulating it as a side effect of a per-item lambda (whose results depend on processing order).
- **Re-evaluation and memory benchmarks** (#53): `IncrementalUpdateBenchmarks` (one source changed in graphs of 16-4,096 sources), `CollectionChangeBenchmarks` (K changed items out of N) and `MemoryOverheadBenchmarks` (building a context vs computing directly), each against a direct, non-incremental baseline. The benchmark smoke test now dry-runs every benchmark in-process, and call-count tests check that the incremental benchmarks recompute only what changed. Results and their interpretation are in the [Performance Guide](docs/performance-guide.md#benchmark-results).
- `IncrementalValueProvider<T>.TryGetValue(out T)` and the None state of `Result<TValue, TError>` (see Breaking).
- **Per-item memoization in collection operators**: a recomputed collection `Select`, `SelectMany` or `Where` runs its lambda only for new or changed items; items equal (by `EqualityComparer<T>.Default`, element-wise for `ImmutableArray<T>` items) to items of its previous computation reuse the previous result instance, so downstream stages hit as well. Pushing or replacing one item of an N-item source runs each recomputed stage's lambda once instead of N times. Items mutated in place are not detected, so keep items immutable (#25).

### Changed

- **Platform upgrade**: all projects target .NET 11 (`net11.0`) with the .NET 11 RC3 SDK pinned in `global.json`, and use `LangVersion=latest` (C# 15). Test projects moved to xUnit v3 on Microsoft.Testing.Platform. Dependencies bumped (Microsoft.Extensions.DependencyInjection 11.0 RC3, Microsoft.SourceLink.GitHub 10.0.403, Microsoft.CodeAnalysis 5.9.0).
- **Release flow**: packages are published to nuget.org only from `v*` version tags (or a manual run of the Publish workflow); the tag name is the package version. Pushes to `main` only build, test and pack. The Publish workflow reuses the CI workflow. Publishing authenticates with nuget.org **trusted publishing** (GitHub OIDC → short-lived API key) instead of a stored `NUGET_API_KEY` secret. Example projects are now part of `guacamole.sln` and built in CI. See [docs/ci-cd.md](docs/ci-cd.md).
- **Snapshot test tooling**: generator snapshot tests use Verify.XunitV3 33.3.4 (from 32.0.1). Verify 33's SponsorCheck build gate is satisfied by its time-bounded OpenSource exemption declared in the test project, valid until 2027-11 and to be renewed before then (#44).
- **Line endings**: all text files are checked out with LF on every platform (`.gitattributes` `* text=auto eol=lf`, matching `.editorconfig`), so CI's `dotnet format --verify-no-changes` check runs on Windows as well as Linux (#50).
- **Benchmark output is no longer tracked** (#58): `dotnet run` in `benchmarks/Guacamole.Benchmarks` writes its reports to BenchmarkDotNet's default `BenchmarkDotNet.Artifacts/` folder in the current directory (git-ignored) instead of overwriting the committed `benchmarks/reports/results/*` files, which were removed. The first committed baseline is kept as a curated copy in [docs/benchmarks/2025-10-baseline.md](docs/benchmarks/2025-10-baseline.md); current results are in the [Performance Guide](docs/performance-guide.md#benchmark-results).
- **Source generator rewrite** (`ComputingContextGenerator`):
  - Cacheable incremental pipeline based on `ForAttributeWithMetadataName`, with all semantic analysis producing equatable models; source and diagnostic outputs are separate branches.
  - Generated code fully qualifies all types with `global::`, so item types from other namespaces work without `using` directives.
  - Unique hint names (namespace + containing types + metadata name), so same-named contexts in different namespaces or types no longer collide.
  - Support for nested contexts (containing types re-emitted as partial), generic contexts and contexts in the global namespace; input properties keep their declared accessibility.
  - New diagnostics: **GUAC0006** (context or a containing type is not `partial`) **GUAC0007** (context does not derive from `ComputingContextBase`), **GUAC0008** (context declares its own parameterless constructor) and **GUAC0009** (constructor never chains to `: this()`). GUAC0003 and GUAC0005 are now reported at the offending property. See [docs/generated-code-reference.md](docs/generated-code-reference.md#diagnostics).
  - The disabled legacy generator and its mutation-method/`SaveChanges` code generators were deleted.
- **Breaking: push-based sources replace mutation methods.** Generated `Add{X}`/`Remove{X}`/`Replace{X}`/`Set{X}` methods, `SaveChanges()`, `SaveChangesAsync()`, `DiscardChanges()` and `HasPendingChanges` were removed. Each input property now gets a `{X}Source` accessor (`IIncrementalSource<T>` with `Push`/`Remove`/`Replace`/`Clear`, or `IIncrementalValueSource<T>` with `Set`), and changes take effect immediately. See [MIGRATION_GUIDE.md](MIGRATION_GUIDE.md).
- **Breaking: version-based lazy invalidation.** A source change only increments the source's version; cached values are revalidated when read, and a provider whose recomputed value is equal keeps its version so dependents stay cached.
- **Equality cut-off at every stage** (#40). Every stage of a pipeline now caches its result with the versions of the inputs it read, not only the providers that are read. Validating a cached value first brings each recorded input up to date (recursively, recomputing it if needed) and then compares its version, so an intermediate stage that recomputes to an equal value (by its comparer) keeps everything downstream of it cached even if that stage is never read itself. Previously such stages were looked through to the sources behind them, and a source change recomputed the whole chain below them. "No value" from a single-value `Where` is cached and takes part in change detection; errors are never cached and always count as a change. Cached reads with no source change since the last verification no longer walk the dependency chain, and no longer allocate.
- **Verification after a change is proportional to the change** (#60). A source change now also marks the stages downstream of it dirty (walking reverse dependency edges recorded as stages read their inputs), and a cached value that has not been marked since it was last verified is valid without looking at its inputs. Reading the root of a 4,096-source reduction tree after one source changed took 2.6 ms (every one of its 16,382 stages re-verified) and now takes about 25 µs (only the changed path). Version lookups on the verification path no longer go through a dictionary. Values verified while a source change is still in progress are not marked clean, so a change racing with a read is still seen by the next read.
- **Collection changes no longer rebuild per-item state** (#61). The per-item memo of collection `Select`/`Where`/`SelectMany` walks the new items in line with the previous ones and updates its item map in place instead of rebuilding it (it still holds exactly the items of the latest computation); `Where` returns its input array when nothing is filtered out; `Collect()` wraps the upstream array instead of copying it; collection sources keep their items in an indexed array with a cached snapshot (O(1) `Push`/`Remove`/`Replace`, no allocation for reads of an unchanged source). Replacing 1 of 10,000 items and reading `Select(work).Collect().Select(Sum)` went from 1.0 ms and 607 KB (with gen2 collections) to about 0.1 ms and 161 KB (the source snapshot and the result array); 100 replacements of 10,000 from 1.4 ms to 0.16 ms. `IIncrementalSource<T>.GetSnapshot()` now returns a read-only view of the shared snapshot instead of a fresh array.
- **Item-level delta propagation in collection pipelines** (#61, second part). Collection sources log the slots each change touches and build their next snapshot from the previous one, with a delta (the inserted, removed and replaced positions). `Select`, `Where`, `SelectMany` and `values.Combine(value)` apply their input's delta to their previous output (copying the unchanged items in bulk and running their lambda, through the per-item memo, only for the edited items) and record the delta of their output; the change checks of these stages and of `Collect()` compare only the replaced items. A stage recomputes in full, as before, when no delta from the input it last read is available (first computation, an input that recomputed more than once in between, more changes between two reads than about half the items, `Clear()`, a storage compaction, custom nodes, errors). Replacing 1 of 10,000 items and reading `Select(work).Collect().Select(Sum)` went from about 108 µs to 34 µs; through `Combine(value).Select.Where.SelectMany.Collect` from 414 µs to 153 µs. Still O(N) per read: each stage allocates its output array and copies the unchanged items into it, and the source copies its snapshot (see the [Performance Guide](docs/performance-guide.md#item-level-deltas)). Nodes that use deltas keep their latest output (and `SelectMany` an offset table) alongside their per-item memo, and a `null` item in an unchanged position now keeps its result instead of rerunning the lambda.
- **`PushRange` adds its items in one step** (#62), with a single change notification (one version change, one run of the output handlers) instead of one per item, and rejects a `null` item before adding any. Building a context over 10,000 items and reading `Select(work).Collect().Select(Sum)` allocated 18.6 MB and took 16 ms; it now allocates 1.2 MB and takes 2.3 ms (the direct computation: 78 KB, 1.1 ms).
- **Several changes between two reads mark the downstream stages once** (#71). A source change marked every stage downstream of it, so K changes before the next read cost K walks over the fan-out. A change now stops at stages that an earlier change has already marked, together with everything downstream of them, since a read last re-verified a value (a read that re-verifies and may record values as clean ends this, so the next change marks again). The soundness argument, including changes racing with reads that re-verify and stamp, is in the remarks of `SharedGraphState.MarkSourceChanged`. With a source read by 10,000 stages, 100 changes before a read cost 3.8 µs per change instead of 376 µs (0.18 µs instead of 3.0 µs with 100 stages); a single change and read is unchanged. `ComputationGraph.InvalidateCacheForNode` follows reverse edges (those recorded as stages read their inputs, and a new reverse index of the graph's declared dependencies) instead of scanning the dependencies of every node for each node it invalidates.
- **Building a graph is no longer quadratic, and metrics cost nothing unless listened to** (#76). `ComputationGraph.AddNode` walked everything upstream of every new node to check for cycles (recursively, so a long enough chain could also overflow the stack), and summed the edges of the whole graph for its graph metrics; building a chain of 1,000 / 4,000 nodes took 111 ms / 2.6 s and allocated 96 MB / 1.5 GB. The graph now keeps a reverse index of its declared dependencies and an edge count: a cycle can only pass through the new node if some node already depends on its ID, so the check is skipped in the usual case (nodes added after their dependencies) and is iterative otherwise. The same chains now take 2.2 ms / 11 ms and 2 MB / 9.7 MB. (Runtime node registration does no cycle check and was already O(1).) Cache, computation and graph metrics are recorded only for instruments a listener has enabled (`Instrument.Enabled`), in addition to the `MetricsConfiguration` switches, and `MetricsConfiguration.Current` no longer takes a lock, which every cache access paid for: an LRU lookup went from 72 ns to 48 ns, a store from 71 ns to 52 ns, and a cached provider read from 80-89 ns to 46-57 ns, with cache metrics on or off. Measured first: with nothing listening, recording itself had cost at most about 15 ns per store; the lock was the larger part.
- **Breaking: property convention reversal.** `partial` get-only provider properties (`{ get; }`) are inputs implemented by the generator; non-`partial` properties with a setter are user-managed. See [docs/migration/010-property-convention-reversal.md](docs/migration/010-property-convention-reversal.md).

### Removed

- Diagnostics **GUAC0001** (duplicate property name) and **GUAC0002** (conflicting type parameters). They could never be reported; their IDs are retired and will not be reused.

### Fixed

- **Batches raised one notification per operation** (#57): `IBatchOperation<T>.Commit()` is documented to commit with a single invalidation, but applied each buffered operation through the source with its own change notification (a version change and a run of the output handlers each). It now applies all operations in order in one step and raises a single notification (none if nothing changed). A batch whose commit throws (for example `Replace` of a missing item) is no longer applied a second time by `Dispose()` (and since #70 applies nothing).
- **`Collect()` compared its result by reference** (#51): `ImmutableArray<T>`'s default equality compares the underlying arrays, so every recompute of a `Collect()` stage counted as a change, bumped its version and reran everything downstream (and fired output handlers registered on it), even when the collected items were equal. Collected arrays are now compared element-wise, in order, with `EqualityComparer<T>.Default`; a re-collect with equal items keeps its version. The new overload `Collect(IEqualityComparer<T> comparer)` compares the items with a custom comparer.
- **Other stages returning `ImmutableArray<T>` still compared by reference** (#59): a single-value `Select`/`Where` whose result is an `ImmutableArray<T>`, collection items that are immutable arrays, and `Combine` tuples containing one used `EqualityComparer<T>.Default`, so such a stage counted as changed on every recompute and defeated the equality cut-off below it (and fired its output handlers). Wherever no comparer is passed, operators now compare `ImmutableArray<T>` results element-wise and value tuples of two or three components containing one component-wise (recursively, so nested arrays and tuples work); other types keep `EqualityComparer<T>.Default`. A comparer passed to the operator still takes precedence. Other collections (`List<T>`, arrays, dictionaries) still compare by reference; pass a comparer for them (see the [Performance Guide](docs/performance-guide.md#equality)).
- **Sources and the per-item memo still compared immutable arrays by reference** (#64): `IIncrementalValueSource<T>.Set` used `EqualityComparer<T>.Default`, so setting an equal but newly built `ImmutableArray<T>` (or a two- or three-component tuple holding one) raised a change notification, bumped the source's version and ran the output handlers. The per-item memo of collection `Select`/`Where`/`SelectMany` keyed items the same way, so over immutable-array items every lambda reran on each recompute. Both now use the same structural default as the operators (element-wise for immutable arrays, component-wise for small tuples of them), as does the change check of stages that have no comparer of their own.
- **Collection sources still compared immutable arrays by reference** (#75): `IIncrementalSource<T>` used `EqualityComparer<T>.Default` for its set semantics and no-op checks, so pushing an equal but newly built `ImmutableArray<T>` added a duplicate, `Replace(a, a')` with an equal array counted as a change, and batches compared items the same way. Collection sources now use the same structural default as the operators. A batch whose operations cancel out also keeps the previous snapshot instance (it raised no notification before either).
- **The value cache's `Set` slowed down as the cache grew** (#68): the LRU cache behind every context indexed its entries with a `ConcurrentDictionary` although every access already took the cache's lock, and read its `Count` on each `Set` (twice with cache metrics on). That `Count` takes all of the dictionary's internal locks, whose number grows with the table up to 1,024, so a `Set` into a cache of 32,000 entries took about 40 µs instead of about 0.2 µs. The index is now a plain `Dictionary` guarded by the cache's lock, and the size is published in a field, so `Set`, `TryGet` and eviction are O(1) at every size. Found by the new complexity checks below.
- **Timing-sensitive tests** (#68): performance tests no longer compare wall-clock times with absolute budgets (for example 100 LRU evictions in under 10 ms), which failed on slow or busy CI runners. O(1) and scaling claims are checked by comparing the time per operation at a small and a large size after a warm-up (best of several runs, a few attempts, ratio bound well below what the regressed complexity would give), and claims about cheap struct operations by measuring allocations, which is deterministic.
- **Collection values could be cast to the cached array and modified** (#69): `IncrementalValuesProvider<T>.GetValues()`/`.Values` (and the values passed to collection output handlers) returned the cached `T[]` typed as `IEnumerable<T>`. That array is shared with downstream stages, `Collect()` results and source snapshots, so `((T[])provider.Values)[0] = x` corrupted all of them. They now return a read-only view (`ReadOnlyCollection<T>`: an `IReadOnlyList<T>` whose `IList<T>` mutators throw `NotSupportedException`), which cannot be cast to an array. The view is kept with the cached value, so a cached read still returns the same instance without allocating (72 ns, 0 B for a 100-item stage, unchanged), and collection output handlers no longer copy the values to compare them with the previous ones. Code that cast the values to `T[]` must copy them (`ToArray()`) instead.
- **Batches are all or nothing** (#70): a `Commit()` whose operation failed (`Replace` of an item that is not present at that point of the batch, or with one that is, or a `null` item) left the operations before it applied and notified. The operations of a batch on a context-created source are now checked against the state they would see before any is applied, so a failing `Commit()` changes nothing and raises no notification. A batch whose operations cancel out (for example `Push` of a new item and `Remove` of it, or `Replace(a, b)` and `Replace(b, a)`) raises no notification either. `Push`/`Remove`/`Replace` on a batch after `Commit()` (also after a failed one) threw nothing and the operation was silently dropped; they now throw `InvalidOperationException`. `Rollback()` after `Commit()` does nothing, so it can be called from an error handler without hiding the `Commit()` exception, and a batch can still be reused after `Rollback()`. Sources that are not created by a context still receive the operations one by one through their own methods.
- **Nodes implementing both node interfaces could lose their reverse edges** (#73): a node implementing both `IComputationNode<T>` and `ICollectionComputationNode<T>` (or one of them for two `T`s) got a second evaluation handle, stored nowhere, when it was read through its other interface. Reverse dependency edges reference handles weakly, so once that handle was collected, source changes stopped reaching the stages reading the node, and a stamped value downstream could be served stale. Every node now has exactly one handle, and a node implementing more than one result interface is rejected on first use with an `InvalidOperationException` naming it (an error result when a downstream stage reads it). The built-in nodes each implement one interface, so pipelines built with the operators are unaffected.
- **A read starting as a change ended could record a stale value as clean** (found while working on #71): an evaluation pass read the graph revision before the source-change state. When a change advanced the revision and ended between the two reads, the pass accepted values verified before that change had incremented its source's version (verified at the older revision) and was still allowed to stamp the values it derived from them, so a stale value could be served until the next change reaching it. A pass now reads the change state first.
- **Custom comparers were ignored**: comparers passed to `Select`/`Where`/`SelectMany` (single-value and collection) were stored but never used, because the operator nodes didn't expose them to the change check. They now decide whether a stage's recomputed result counts as a change, both for the cache cut-off and for output handlers registered on that stage (which previously always used `EqualityComparer<T>.Default`).
- **Node reuse**: identical operator calls (same operator, same ordered inputs, equal delegates and comparers) return the existing node, so pipelines built repeatedly (e.g. in property getters with non-capturing lambdas) share one cache and don't grow the graph.
- **Node ID collisions**: node IDs were derived from the operation name and parent IDs, so two different operator calls on the same parent (for example two `Select`s with different lambdas) shared one cache slot and could return each other's values. Every operator call now creates a node with a unique ID.
- **Caching after source changes**: derived values are kept cached across source changes and are recomputed only when an input they depend on has changed. A source's version is recorded before its value is read, so a change that happens during a computation is picked up by the next read.
- **Thread safety**: `LRUCache.TryGet` performs lookup, LRU update and value read atomically; storing a computed value with its version information is atomic; output registration, source subscription and `Dispose()` are synchronized.
- **Output handlers**: all registered handlers run even if one throws; afterwards the exceptions are rethrown together as an `AggregateException`.
- **Dispose**: disposing a context unsubscribes it from its sources (so they neither keep it alive nor notify it) and clears its output registrations; notifications that race with `Dispose()` are ignored.
- **Collection operators**: exceptions thrown by lambdas in collection `Select`/`Where`/`SelectMany` are returned as error results instead of escaping during enumeration.
- **Generated code**: compiles without errors or warnings for item types from other namespaces, nested and generic contexts (verified by snapshot tests that compile the output).
